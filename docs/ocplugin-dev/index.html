.ocplugin 插件开发手册

从空白目录到可安装的单文件插件

适用于 OpenCode 2.2.x · 桌面版 · Bun 1.3 以上  |  本文档为纯静态 HTML，无脚本、无外部资源

1. 简介与名词

.ocplugin 是 OpenCode 的单文件插件格式。一个文件里包含服务端入口、可选的界面入口、技能正文和随包数据。 用户安装后，它被解包成普通插件目录，由宿主自动发现、加载和热更新。

名词 含义
服务端入口 在 OpenCode 服务进程里运行的代码，负责注册工具、技能、hooks。文件通常叫 server/index.js。
GUI 入口 在桌面应用窗口里运行的界面代码，CommonJS 文件，通常叫 gui-experimental.cjs。
主进程入口 GUI 入口里的 main 字段，在 Electron 主进程运行，可操作窗口、菜单、系统能力。
清单 ocplugin.json，描述 id、版本、入口、展示信息。
安装目录 ~/.opencode/ocplugins/<id>/，宿主监听此目录，放入即加载。

2. 工程目录

2.1 完整目录树

下面是一个同时带服务端工具、技能和界面挂件的完整工程，可直接照此创建：

echo-plugin/
├── ocplugin.json              # 【必需】插件清单
├── package.json               # 【必需】工程依赖与脚本
├── tsconfig.json              # 【可选】TypeScript 配置
├── vite.config.ts             # 【可选】只在有界面时需要
├── src/
│   ├── index.ts               # 【必需】服务端入口
│   └── gui.tsx                # 【可选】界面入口
├── skills/
│   └── echo/
│       └── SKILL.md           # 【可选】技能正文
├── script/
│   ├── build.ts               # 【必需】构建脚本
│   └── pack.ts                # 【必需】打包脚本
└── dist/                      # 构建产物（不提交）
    ├── ocplugin.json          # 打包时重写为带校验和的版本
    ├── package.json           # 解包后解析入口用
    ├── server/index.js        # 服务端入口
    ├── gui-experimental.cjs   # 界面入口（有界面时）
    └── skills/echo/SKILL.md   # 技能正文

2.2 各文件的作用

文件 谁读它 作用
ocplugin.json 安装器、插件目录 校验 id/版本/完整性，展示名称与描述。
package.json（工程） Bun 开发依赖与 build/pack 脚本。
src/index.ts 服务进程 默认导出 Plugin.define，注册工具、技能、hooks。
src/gui.tsx 桌面窗口 默认导出 GUI 的 Plugin.define，注册界面。
script/build.ts 开发者 编译入口、生成 dist/package.json、拷贝静态文件。
script/pack.ts 开发者 把 dist/ 打成 .ocplugin，写入校验和。
dist/ 安装器、宿主 解包后的插件目录内容。

2.3 ocplugin.json

echo-plugin/ocplugin.json{
  "apiVersion": 1,
  "id": "opencode.echo",
  "version": "0.1.0",
  "requires": { "opencode": "^2.2.0" },
  "entry": {
    "server": "server/index.js",
    "gui": "gui-experimental.cjs"
  },
  "externals": [
    "effect",
    "@opencode/plugin",
    "@opencode/schema"
  ],
  "display": {
    "name": "Echo",
    "description": "把文本原样返回，并演示界面挂件。",
    "category": "demo",
    "tools": ["echo"],
    "skills": [
      {
        "id": "echo",
        "name": "Echo",
        "description": "使用 echo 工具把文本原样返回。"
      }
    ]
  },
  "skills": [
    {
      "id": "echo",
      "name": "Echo",
      "description": "使用 echo 工具把文本原样返回。",
      "path": "skills/echo/SKILL.md"
    }
  ],
  "assets": []
}

字段说明

字段 类型 必需 说明
apiVersion number 是 当前只接受 1；更高版本提示用户升级应用。
id string 是 插件身份，同时是安装目录名。不能与内置插件 id 相同或前缀交叉。
version string 是 语义化版本。同 id 新版本会替换安装目录。
requires object 否 声明所需 OpenCode 版本。当前安装器不校验，仅作文档。
entry.server string 是 服务端入口相对路径。安装时校验文件存在。
entry.tui string 否 TUI 入口。实际加载仍由包内 package.json 决定。
entry.rpc string 否 RPC 契约入口。
entry.gui string 否 声明用。当前加载逻辑不读它，见 2.4。
externals string[] 否 由宿主提供、不打进产物的模块。安装时软链到插件 node_modules。
display.name string 否 插件目录显示的名称。
display.description string 否 一句话描述。
display.category string 否 插件目录的分组名。
display.tools string[] 否 工具名前缀，如 echo、acme.*。
display.skills array 否 展示用技能列表，字段 id、name、description。
skills array 否 技能清单，额外带 path。仅供运行时读取，不自动注册。
assets string[] 否 随包数据目录，说明用。
files array 打包生成 { path, sha256 }[]，安装时逐项校验。

2.4 package.json（解包后的入口声明）

解包后的目录是一个普通插件包，宿主按包内 package.json 的 exports 找入口。 这个文件由 build.ts 生成，不手写。 

dist/package.json{
  "name": "opencode.echo",
  "version": "0.1.0",
  "type": "module",
  "main": "./server/index.js",
  "exports": {
    ".": "./server/index.js",
    "./gui-experimental": "./gui-experimental.cjs"
  }
}

解析规则，按顺序：

  1. 有 package.json 且声明 exports：按 .、./server、./tui、./rpc、./gui-experimental 解析。
  2. 没有 exports：按约定文件名找 server/、tui/、rpc/、gui-experimental.cjs|js。
重要：ocplugin.json 里的 entry.gui 不参与加载。界面必须写进这里的 exports["./gui-experimental"]，否则界面永远不会出现。

2.7 src/index.ts（服务端入口）

默认导出一个 Plugin.define。id 必须与清单一致；setup 在插件加载时执行。 

echo-plugin/src/index.tsimport { Plugin } from "@opencode/plugin"
import { Schema } from "effect"

export default Plugin.define({
  id: "opencode.echo",

  async setup(ctx) {
    // 注册工具
    await ctx.tool.transform((tools) => {
      tools.add({
        name: "echo",
        description: "Echo the given text back to the caller.",
        input: Schema.Struct({ text: Schema.String }),
        output: Schema.Struct({ text: Schema.String }),
        execute: async ({ text }) => ({ output: { text }, content: text }),
      })
    })
  },
})

echo-plugin/src/gui.tsximport { Command, Plugin, Slot } from "@opencode/plugin/gui"

export default Plugin.define({

  return (
    <div style={{ position: "fixed", insetInlineEnd: "16px", bottom: "12px", "z-index": 10 }}>
      <button type="button" onClick={() => setTouched((value) => value + 1)}>

  )
}

2.10 script/build.ts

构建分三件事：编译服务端、可选编译界面、生成 dist/package.json 并拷贝静态文件。

echo-plugin/script/build.tsimport { cp, mkdir, rm, writeFile } from "node:fs/promises"
import { join } from "node:path"

const root = join(import.meta.dir, "..")
const dist = join(root, "dist")
const manifest = await Bun.file(join(root, "ocplugin.json")).json()

await rm(dist, { recursive: true, force: true })
await mkdir(join(dist, "server"), { recursive: true })

// 1. 服务端入口
const build = await Bun.build({
  entrypoints: [join(root, "src/index.ts")],
  target: "bun",
  format: "esm",
  outdir: join(dist, "server"),
  naming: "index.js",
  external: [...manifest.externals, "node:*"],
})

if (!build.success) {
  for (const log of build.logs) console.error(log)
  process.exit(1)
}

// 2. 静态文件
await cp(join(root, "skills"), join(dist, "skills"), { recursive: true }).catch(() => undefined)
await cp(join(root, "ocplugin.json"), join(dist, "ocplugin.json"))

// 3. 解包后的入口声明：只有真的产出了界面才声明
const gui = await Bun.file(join(dist, "gui-experimental.cjs")).exists()
const exports = {
  ".": "./server/index.js",
  ...(gui ? { "./gui-experimental": "./gui-experimental.cjs" } : {}),
}

await writeFile(
  join(dist, "package.json"),
  JSON.stringify(
    {
      name: manifest.id,
      version: manifest.version,
      type: "module",
      main: "./server/index.js",
      exports,
    },
    null,
    2,
  ) + "\n",
)

console.log(`built ${manifest.id} ${manifest.version} -> ${dist}`)
顺序：有界面时先执行 bunx vite build 生成 gui-experimental.cjs， 再执行 bun run script/build.ts。否则 dist/ 会被清空，界面文件也随之丢失。

3. 打包与分发

3.1 包格式

.ocplugin 是 gzip 压缩的 tar 包。根目录必须有 ocplugin.json，且清单里带 files 校验和。 

opencode.echo-0.1.0.ocplugin  (gzip tar)
├── ocplugin.json     <- 带 files[].sha256
├── package.json
├── server/index.js
├── gui-experimental.cjs
└── skills/echo/SKILL.md

3.2 script/pack.ts

echo-plugin/script/pack.tsimport { createHash } from "node:crypto"
import { mkdir, readdir, readFile } from "node:fs/promises"
import { homedir } from "node:os"
import { join, relative, sep } from "node:path"

const root = join(import.meta.dir, "..")
const dist = join(root, "dist")
const manifest = await Bun.file(join(root, "ocplugin.json")).json()

async function walk(directory: string): Promise<string[]> {
  const entries = await readdir(directory, { withFileTypes: true })
  const nested = await Promise.all(
    entries.map((entry) => {
      const full = join(directory, entry.name)
      return entry.isDirectory() ? walk(full) : [full]
    }),
  )
  return nested.flat()
}

const paths = (await walk(dist))
  .map((file) => relative(dist, file).split(sep).join("/"))
  .filter((path) => path !== "ocplugin.json")
  .sort()

const files: Record<string, Uint8Array> = {}
const checks: { path: string; sha256: string }[] = []

for (const path of paths) {
  const bytes = new Uint8Array(await readFile(join(dist, ...path.split("/"))))
  files[path] = bytes
  checks.push({ path, sha256: createHash("sha256").update(bytes).digest("hex") })
}

files["ocplugin.json"] = new TextEncoder().encode(
  JSON.stringify({ ...manifest, files: checks }, null, 2) + "\n",
)

const out = join(homedir(), ".ocplugins-local", manifest.id, manifest.version)
await mkdir(out, { recursive: true })

const archive = join(out, `${manifest.id}-${manifest.version}.ocplugin`)
await Bun.Archive.write(archive, files, { compress: "gzip", level: 9 })

// 插件目录读取的侧车清单，不必解压
await Bun.write(join(out, "manifest.json"), JSON.stringify(manifest, null, 2) + "\n")

console.log(`packed ${archive}`)

执行：

终端bun run script/pack.ts

3.3 打包规则

规则 说明
文件清单 dist/ 下所有普通文件，路径用 / 分隔。
清单重写 包根 ocplugin.json 由打包脚本重写，包含 files[].sha256。
自引用 ocplugin.json 不列入 files，避免循环。
输出位置 ~/.ocplugins-local/<id>/<version>/<id>-<version>.ocplugin。
侧车清单 同目录 manifest.json（不含 files），供插件目录快速读取。
压缩 gzip，压缩级别 9。
确定性 Bun.Archive 写入当前时间戳，两次打包 sha256 不同。需要可复现构建请手写 tar 头（见 3.6）。

3.4 安装与自动加载

  1. 放入待安装目录

    把 .ocplugin 放到 ~/.ocplugins-local/<id>/<version>/。

  2. 在应用中安装

    打开 Explore 页的插件列表，找到该条目，点安装。

  3. 安装器校验

    • apiVersion === 1
    • 清单 id 与请求 id 一致
    • 版本一致（若指定）
    • 每个 files[].sha256 匹配

  4. 解包

    解包到 ~/.opencode/ocplugins/<id>/，并按 externals 把宿主模块软链进插件的 node_modules。

  5. 自动加载

    安装根目录被监听，文件变化触发重新加载：服务端重新执行 setup，广播 plugin.updated，桌面主进程把界面推给窗口。全程不需要重启应用。

3.5 版本与升级

安装新版本时，安装器删除同 id 的旧目录再解包。Windows 上已被加载的文件可能无法删除，此时会明确报错而不是假装成功。 版本号必须递增，否则安装器认为已安装并直接返回。

3.6 分发方式

方式 做法 适用
单文件 把 .ocplugin 发给对方，放进 ~/.ocplugins-local/<id>/<version>/ 后安装。 手动试用、离线环境
目录 直接把 dist/ 拷到 ~/.opencode/ocplugins/<id>/，无需打包。 本地开发
可复现构建 手写 tar 头，路径排序、mtime 归零，参考 packages/plugins/webwright/script/pack.ts。 发布、校验
npm / Git 包 不打包，配置 plugins 指向包名或本地目录。 团队内部、持续更新
安全提示：安装器只做 sha256 完整性校验，没有签名与来源验证。不要把来源不明的 .ocplugin 放进安装目录——它会在服务进程和桌面窗口里执行任意代码。

4. API 参考

插件有两套上下文：服务端 ctx 运行在 OpenCode 服务进程，界面 ctx 运行在桌面窗口， 两者之外还有主进程 main(ctx)。下面逐项列出。

4.1 服务端上下文总表

属性 类型 / 方法 说明
ctx.appname、version、channel当前 OpenCode 应用信息。
ctx.locationLocation.Info插件运行的工作区位置。
ctx.optionsRecord<string, any>配置里给插件的 options。
ctx.agenttransform、reload增删改 agent。
ctx.aisdkhook("sdk" | "language")替换 AI SDK 模块或语言模型。
ctx.commandtransform、reload服务端命令。
ctx.credentialactivate激活凭据。
ctx.eventsubscribe订阅服务端事件。只用 types 过滤后的事件，见 4.15。
ctx.experimentalterminal.read、generate.text、artifact实验性能力。
ctx.integrationtransform、reload、connection外部集成。
ctx.mcptransform、reloadMCP 服务器。
ctx.modeltransform、reload模型列表与限制。
ctx.permissionlist、get、reply、assert、hook权限规则与询问。
ctx.pluginlist已加载插件列表。
ctx.providertransform、reload模型提供商。
ctx.referencetransform、reload引用源。
ctx.rpc按契约调用、register跨进程、跨插件的 RPC 契约，见 4.16。
ctx.session见 4.4会话操作与 hooks。
ctx.shellhookshell 执行钩子。
ctx.skilltransform、reload技能注册。
ctx.storageget、set、remove、scan异步，值只能是纯 JSON。三套存储语义见 4.14。
ctx.tooltransform、reload、list、hook模型工具。
ctx.vcstransform、reload版本控制。
ctx.websearchtransform、reload联网搜索提供商。
ctx.worktreetransform、reload工作树策略。

字段类型说明

4.14 声明（Declarations）

Plugin.define 除 id / setup / main 外，还有一组声明： os、i18n、stores。宿主在任何 setup 执行之前读取它们， 所以声明里不能引用运行时才知道的值。 

src/gui.tsxexport default Plugin.define({
  os: ["macos", "windows"],
  i18n: { en: { title: "Acme" }, "zh-CN": { title: "Acme 工具" } },
  stores: {
    prefs: Store.global(Prefs, { shown: true }, "plugin.acme.settings"),
    view: Store.session(View, { open: [] }),
  },
  setup(ctx) {
    const shown = () => ctx.stores.prefs.value.shown
    const open = (session) => ctx.stores.view(session).value?.open ?? []
  },
})

os

值含义
"macos"macOS。
"windows"Windows。
"linux"Linux 及其他桌面平台。

省略表示全平台。从配置安装的插件只在桌面版运行；内置插件若列出了任一 OS，则在 Web 端不运行 （Web 端没有可判断的 OS）。

i18n

形状是 { en: Messages } & { [locale: string]: Messages }。

  • Messages 是 Record<string, string>：键到模板。
  • 英文必填，同时作为其他语言缺失键的兜底。
  • 插值写 {{name}}，由 ctx.t(key, { name }) 填充。
  • 复数键带 CLDR 后缀，如 files.one / files.other，用 ctx.plural("files", 3) 读取；{{count}} 自动填入。

ctx.t 的回退链：先查插件字典，再交给应用的语言模块解析共享键（如 common.*）。 ctx.plural 则先读 <key>.<category>，再读 <key>.other。

stores

用 Store.global 或 Store.session 声明。键名就是 ctx.stores 上的属性名， 实际存储键是 plugin.<id>.<name>。

工厂作用域读取
Store.global(schema, initial, from?) 整个应用一份，setup 之前加载完成 ctx.stores.prefs.value，永不为 undefined
Store.session(schema, initial, from?) 每个会话一份，会话挂载时开始加载 ctx.stores.view(session).value，加载完成前与位置未知时为 undefined

schema 必须是对象 schema。字段缺失或解码失败时取 initial； 整体解码失败时读作 initial。

from 是一次性的旧键迁移：只在该 store 还没有值时导入，可以是单个键或「从新到旧」的列表 （第一个有值的被导入）。例如 Store.global(Prefs, { shown: true }, "plugin.acme.settings")。 旧键会保留自己的副本，直到用 ctx.storage.remove 连 from 一起删除。

每个声明出来的 store 都是 Persisted，有四个成员：

成员说明
value存储值；窗口里是响应式的，加载完成前为 undefined（global store 例外）。
ready()是否已加载；主进程里恒为 true。
update(draft => undefined)在深可变草稿上原地修改；不能返回替代值。
set(next)整体替换，用于原始类型或替换整个对象。

三套存储的差别

位置接口同步说明
服务端 ctx.storage get、set、remove、scan 否（Promise） 值必须是 Schema.Json，即纯 JSON。
GUI 窗口 ctx.storage store(key, { schema, initial, scope, from })、memory(key, { initial })、remove(key, { scope, from }) 否（响应式） 给运行时才知道的键用（例如按服务器与目录生成的键）。memory 只活在当前窗口，插件重载后仍在，窗口重载后丢失。
GUI 窗口 ctx.stores 声明式，见上 否（响应式） 键在定义时就已知时优先用它，宿主负责在读取前加载。
主进程 ctx.storage store(key, options)、remove(key) 是 同步读写，跨窗口共享；主进程没有声明式 stores。

4.15 事件订阅

两个入口读同一条公开事件流，但传输方式和拿得到的东西不同：

入口传输server.connected
服务端 ctx.event.subscribe(options?) 进程内事件总线，返回异步可迭代对象 拿不到：类型上已排除
GUI 窗口 ctx.client.event.subscribe(options?) HTTP SSE，连本地服务端 能拿到：每次连接的首帧必定是它；订阅时若流已就绪，也会立刻收到一次

SubscribeOptions 只有三个字段：

字段说明
types?事件类型白名单。省略会收到全部事件。
signal?中断订阅。
onActivity?传输层活动回调，包含不带事件的 keepalive 帧。

没有 after 游标：断线期间的事件不会补发。GUI 侧收到 server.connected、 或任一入口收到活动信号后，重新拉一次状态快照，不要假设事件是连续的。 

服务端for await (const event of ctx.event.subscribe({
  types: ["session.execution.succeeded", "session.execution.failed", "session.execution.interrupted"],
})) {
  if (event.type === "session.execution.succeeded") {
    // event.properties.sessionID
  }
}
界面for await (const event of ctx.client.event.subscribe({
  types: ["session.execution.succeeded"],
  signal: ctx.signal,
})) {
  // server.connected 也会出现在这里，可用来触发一次重拉
}

必须用 types 过滤

session.text.delta、session.reasoning.delta 在生成时每秒几十条； 不过滤会让界面与服务端都被无意义的事件占满。只订阅真正要处理的那几个类型。

判断「任务结束」

用 session.execution.succeeded / .failed / .interrupted， 不要用 session.status 或 session.idle：

  • session.status 是 ephemeral 的整体状态（idle / busy / retry），断开即丢。
  • session.idle 已废弃，不要用。
  • 子 agent 会话也会发 session.execution.*，需要时按 parentID 过滤。

durable 与 ephemeral

下表按持久性分列。durable 写入事件日志，可被回放；ephemeral 不落盘，断开即丢， 只能靠重新拉快照补齐。ephemeral 列共 7 个在用事件，另有已废弃的 session.idle。

分组durableephemeral

步骤 session.step.started、session.step.streamed、session.step.ended、session.step.failed —
文本 session.text.started、session.text.ended session.text.delta
推理 session.reasoning.started、session.reasoning.ended session.reasoning.delta

4.16 RPC（服务端）

ctx.rpc 是服务端侧的 RpcDomain：用 @opencode/plugin/rpc 的 Rpc.define 定义契约，走服务端的 RPC 端点，可以被其他插件与界面调用。

调用方

契约import { Rpc } from "@opencode/plugin/rpc"
import { Schema } from "effect"

export const Acme = Rpc.define({
  id: "acme.search",
  methods: {
    search: {
      input: Schema.Struct({ query: Schema.String }),
      output: Schema.Struct({ hits: Schema.Array(Schema.String) }),
    },
  },
})
调用const client = ctx.rpc(Acme)
const { hits } = await client.search({ query: "ocplugin" })
const stop = client.on("indexed", (data) => { ... })

提供方

服务端const registration = await ctx.rpc.register(Acme, {
  async search(input, context) {
    if (context.signal.aborted) return context.error.Aborted()
    return { hits: [] }
  },
})

await registration.events.emit("indexed", { count: 3 })
成员说明
ctx.rpc(definition)返回客户端：每个方法一个异步函数，另有 on(name, listener) 订阅该契约的事件。
ctx.rpc.register(definition, handlers)注册实现。每个 handler 收到 (input, context)，context 有 signal 与错误工厂 error。返回对象含 events.emit(name, data)。

与 4.17 的区别：ctx.rpc 是服务端契约，跨进程按 RPC 端点寻址； 窗口桥的 Ipc 只在自己的主进程与自己的窗口之间传递。

4.17 窗口桥（Ipc / Contract）

界面侧有两套进程间/插件间通信，别混用：

机制范围定义提供读取
Contract 同一进程内（窗口到窗口） Contract.define<T, Id>(id) ctx.provide(token, impl) ctx.use(token)
Ipc 插件的主进程与它的窗口，走 Electron 桥 Ipc.define({ id, state?, methods, events? }) 主进程 ctx.provide(token, impl) ctx.main(token)（自己的）/ ctx.use(token)（别人的）

Ipc 定义

契约import { Ipc } from "@opencode/plugin/gui"
import { Schema } from "effect"

export const Pairing = Ipc.define({
  id: "pairing",
  state: Schema.Struct({ active: Schema.Boolean }),
  methods: {
    screenActive: { output: Schema.Boolean },
  },
  events: {
    paired: Schema.Struct({ device: Schema.String }),
  },
})

主进程提供

mainlet active = false
const provider = ctx.provide(Pairing, {
  state: () => ({ active }),
  screenActive: async () => active,
})

// 状态变化后推给窗口；不调用时窗口读到的是上一次快照
active = true
provider.changed()
provider.emit("paired", { device: "phone" })

窗口读取

guiconst pairing = ctx.main(Pairing)
pairing.state()            // 主进程最后一次推送的状态，未到达前为 undefined
const active = await pairing.screenActive()
const stop = pairing.on("paired", (data) => { ... })
成员说明
方法调用IpcClient 上每个方法一个异步函数：输入按 schema 编码、回复按 schema 解码；编码失败、Ipc 已撤销或主进程抛错时 reject。
state()本窗口看到的状态，响应式；事件总是胜过更旧的快照。Ipc 撤销后回到 undefined。
on(name, listener)监听一个事件，返回移除函数。随当前 owner（如某个 createKeyed 作用域）或插件一起移除。
IpcProvider.changed(window?)重新读取 impl.state 并推给订阅的窗口；传窗口 id 只推一个。
IpcProvider.emit(name, data, window?)发一个事件；编码失败写日志而不抛错，未知事件名抛错。
IpcProvider.dispose()提前撤销。窗口看到它处于 pending，调用会等待，直到重新提供或实例销毁。

Ipc 的 id 必须是插件自己的 id 或其子路径（<id>.<name>），否则 ctx.provide 抛错。 实例销毁时宿主自动撤销它提供的一切；窗口侧看到的是「等待」，不是错误。

5. 调试

5.1 确认插件被加载

在 setup 开头写一行日志：

src/index.tsexport default Plugin.define({
  id: "opencode.echo",
  async setup(ctx) {
    console.log("[echo] loaded")
    ...
  },
})

覆盖安装目录后看服务端日志。没有这一行说明插件没有被发现或加载失败。

5.2 确认界面被加载

  1. 插件处于启用状态。
  2. dist/package.json 有 "./gui-experimental"。
  3. bundle 是 CommonJS，不含 import/export 语句。
  4. 在桌面端运行；Web 端不加载第三方界面。

5.3 确认工具被调用

  1. 让模型「列出可用工具」，看工具名是否出现。
  2. 直接要求调用，观察时间线里的参数与结果。
  3. 输入 Schema 不匹配时，模型会收到校验错误并可能自行重试。

5.4 热更新不生效

  1. 确认覆盖的是 ~/.opencode/ocplugins/<id>/，不是项目里的 dist/。
  2. 确认构建产物时间戳已更新。
  3. 手动触碰目录：touch ~/.opencode/ocplugins/<id>。

8. 能力边界与常见问题

能力边界

下面是「能不能做桌面级能力」这个问题的准确答案，按代价从低到高排列。

一、只差公开暴露（内部已实现）

能力现状
已有窗口的读取与事件 ctx.windows.get/list/focused/on 已公开，是唯一受支持的窗口入口。
页面嵌入 ctx.embeds.create(view, window) 把 WebContentsView 放进已有窗口布局。
显示器信息 主进程内部已有 screen.getAllDisplays 等封装（窗口状态恢复在用），尚未作为 ctx 成员公开。

二、需要新增受管实现

这些能力本身在 Electron 里存在，主进程 bundle 也能 require("electron")，缺的是公开 API、 生命周期绑定和权限声明。不做这些，插件只能走非公开路径，插件重载或停用后资源会残留。

能力缺什么
Overlay 窗口（透明、无框、置顶、穿透）创建 API、渲染入口、窗口类型标记、与插件实例绑定的销毁。
托盘图标创建、菜单、点击事件；仓库里没有现成的 Tray 封装。
全局快捷键注册、冲突检测、按插件隔离与自动释放；仓库里没有 globalShortcut 封装。
开机自启该设置属于整个应用，多插件会互相覆盖，需要宿主合并后才能公开。

三、需要改架构

补 overlay 前必须先解决，否则会污染主窗口的恢复与退出语义：

  • 事件广播目前只发给注册的主窗口，overlay 窗口收不到插件事件。
  • 渲染入口没有窗口类型分支，overlay 需要与主窗口共用同一份 renderer bundle，靠启动参数区分。
  • window-all-closed 与 activate 会把 overlay 当成主窗口，导致「还有窗口就不退出」的错误判断。

四、明确不做

  • 把 BrowserWindow 或 webContents 实例直接交给插件：无法撤销，插件重载后窗口残留。
  • 为插件新增独立 HTML 入口：插件 bundle 的求值依赖应用的模块白名单，独立入口会绕开它。
  • 清单字段 entry.gui / entry.tui / entry.rpc 的自动消费：当前安装器只读 entry.server，写这些字段不会产生任何效果。

尚未实现

下面三项在文档里不写成已有能力，属于路线图：

项现状
事件补发（after 游标）SubscribeOptions 只有 types / signal / onActivity，没有游标；durable 事件无法从指定位置续订，ephemeral 事件永远无法补发。
permissions 声明ocplugin.json 没有权限字段，安装时也没有逐项授权提示；安装器只校验 entry.server。
requires（最低宿主版本）只有 apiVersion 且必须等于 1，没有表达「需要某个更高的宿主版本」的字段。

Q: 清单里写了 entry.gui，界面为什么不出来？

加载逻辑只读 entry.server。界面入口必须写进包内 package.json 的 exports["./gui-experimental"]，或把 gui-experimental.cjs 放在包根。

Q: 能做独立桌面窗口吗？

公开 API 只提供已有窗口的读取（ctx.windows）与页面嵌入（ctx.embeds）。 主进程入口可以 require("electron") 自行创建窗口，但属于非公开路径，升级不保证兼容， 也不受插件生命周期管理。哪些能力只差暴露、哪些要改架构、哪些明确不做，见上文「能力边界」。

Q: 能不能直接改 OpenCode 的内置界面？

不能替换内置组件的渲染逻辑。可以新增注册表条目、插槽内容，或注入 CSS 与主题； 与内置插件同 id 的插件会被判定冲突，界面不加载。

Q: 为什么工具参数校验失败？

input 用了 Effect Schema，字段名与类型必须与模型传入一致。给字段加 Schema.optional 可以让参数变为可选。

Q: 打包后安装提示校验失败？

检查生成校验和的是否就是最终写入压缩包的字节。先写文件再计算哈希，不要在打包后修改 dist/。

Q: 插件可以同时有服务端与界面吗？

可以，同一个包内放 server/index.js 与 gui-experimental.cjs， 清单和 package.json 同时声明两个入口即可。界面通过 ctx.client 或 ctx.rpc 调用服务端。
