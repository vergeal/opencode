.ocplugin 插件开发手册

从空白目录到可安装的单文件插件

适用于 OpenCode 2.2.x · 桌面版 · Bun 1.3 以上  |  本文档为纯静态 HTML，无脚本、无外部资源

1. 简介与名词

.ocplugin 是 OpenCode 的单文件插件格式。一个文件里包含服务端入口、可选的界面入口、技能正文和随包数据。 用户安装后，它被解包成普通插件目录，由宿主自动发现、加载和热更新。

名词 含义
服务端入口 在 OpenCode 服务进程里运行的代码，负责注册工具、技能、hooks。入口是 server/main.ts（或编译后的 server/main.js）。
GUI 入口 在桌面应用窗口里运行的界面代码，CommonJS 产物，入口是 gui/main.cjs（源码 gui/main.tsx）。
主进程入口 GUI 入口里的 main 字段，在 Electron 主进程运行，可操作窗口、菜单、系统能力。
清单 ocplugin.json，描述 id、版本、入口、展示信息。
安装目录 ~/.opencode/ocplugins/<id>/，宿主监听此目录，放入即加载。

2. 工程目录

2.0 入口标准（Entry Contract）

入口的文件名与目录名决定了插件能不能被加载。ocplugin.json 的 entry 是唯一权威： 每个部件声明成「相对插件根目录、不含扩展名、以 /main 结尾」的路径，宿主再按该部件的扩展名顺序去找文件。

项规则
入口文件名 固定为 main。每个部件用自己的目录，目录名 = 入口名：server/、gui/、tui/、rpc/。
entry 的值 相对插件根目录、不含扩展名、以 /main 结尾，例如 server/main。 不能以 / 或 ./ 开头，不能含 .. 段。 schema 校验这个形状；不合规的条目按没写处理，走下面的旧路径回退而不是直接报错。
server / tui / rpc 的扩展名 按 .ts → .tsx → .js → .mjs 取第一个存在的文件。
gui 的扩展名 按 .js → .cjs 解析，必须是 CommonJS：应用用 eval 执行 CJS 文本，TS 源码与 ESM 都不能作为界面入口。
package.json 不参与本地目录的入口解析，但要存在：清单没写 id 时，宿主用 packageID 读它的 name 兜底（再退到目录名）；从 npm 安装的包还要靠它自己的 exports 解析入口（过渡回退，见下）。
打包产物 产物目录结构与源码一致，打包不改写 ocplugin.json。允许 dist/server/main 这类前缀，文件本身仍叫 main。 
ocplugin.json{
  "entry": {
    "server": "server/main",
    "gui": "gui/main"
  }
}
my-plugin/
├── ocplugin.json
├── package.json
├── tsconfig.json
├── server/
│   └── main.ts
├── gui/
│   └── main.tsx
└── skills/

旧路径的回退（过渡性，非永久）

入口解析是三步。回退是正常加载，不是宽容错误：

  1. 先按 entry 声明的 main 找，按该部件的扩展名顺序取第一个存在的文件。
  2. 找不到就回退到旧路径，照常加载，同时打一条 deprecation 警告。
  3. 新旧都没有才拒绝，错误信息列出全部候选文件（见 6）。
部件回退顺序
serverserver/index、src/index、index
tuitui/index、tui
rpcrpc/index、rpc
guigui/index、gui-experimental

main 与旧入口并存时用 main，不报警告：警告只在真的走到旧路径时出现。

警告长什么样

加载路径（packages/core/src/plugin/module.ts）记一条结构化日志，不是拼接字符串： 

服务端日志msg:      "plugin uses a legacy entry"
target:   "/Users/…/ocplugins/opencode.webwright"   # 插件目标或 id
kind:     "server"
found:    "server/index"                            # 实际命中的旧路径
expected: "server/main"                             # 应该改成的路径

Host.resolve 本身是纯函数：只返回 deprecated 列表，由调用点决定怎么记。 配置发现与 plugin list 只把它当数据、不记日志——那两条路径在每次配置变化或列表刷新时都会跑， 每次都警告会刷屏。所以同一个插件可能「列表里已经出现」但日志还没警告。 安装期（packages/core/src/plugin/bundle.ts）仍是控制台警告： 

服务端日志[opencode] Plugin "test.bundle" server entry "server/index" is deprecated; this bundle should declare and ship "server/main".
只进服务端日志。这类警告没有界面通道、不需要 i18n：插件列表、设置页、toast 都不会提示。 它是给开发者查日志用的，用户看不到。

安装期同样接受旧路径（带警告）。只有「entry 指向的文件在压缩包里根本不存在」这类真正不合规的形态才拒绝安装， 错误为第 6 章的 no <kind> entry ... tried ...。等回退按下面的条件移除，旧路径才会重新变成硬性拒绝。

通过 npm 安装的包仍走 package.json 的 self-reference / exports （<name>/server、<name>、<name>/tui、<name>/rpc、 <name>/gui-experimental）作为过渡回退。这条与上面的旧路径一起，按同样的条件移除。

新插件不要依赖回退：它能加载，但每次都会打 deprecation 警告。 从零创建用 2.12 的脚手架，生成的清单直接符合本节规则。

回退什么时候移除

回退不会因为「过了下个 minor」就自动消失：只有在四条全部满足后才删——

  1. packages/plugins/* 的内置插件全部在 ocplugin.json 声明 main，且源码布局符合标准（目录名 = 入口名）。
  2. 本文档不再出现旧路径写法，2.0 里的旧行为描述与迁移对照表已删除。
  3. 至少经过一个 minor 的 deprecation 周期，并在 CHANGELOG.md 记录。
  4. 真实加载路径上不再出现回退警告。

移除回退本身是一次独立的行为变更，必须在同一次改动里完成：

  • 删回退代码与 LegacyEntrypoints 列表。
  • 删「旧入口仍可加载并警告」的回归测试，新增「旧入口被拒绝」的测试。
  • 删掉 module.ts 里那处 plugin uses a legacy entry 警告。
  • 删本文档 2.0 的「旧路径的回退」整节：回退顺序表、npm self-reference 回退段、 「旧布局已废弃」的 note，以及第 6 章错误表里 tried 列出的旧候选。 条件 2 就是这一步的验收——只改代码、不改文档，条件 2 永远不满足。
  • 第 6 章的 A plugin's ./gui-experimental bundle must default-export a Plugin.define 是宿主真实抛出的文案，撤回退前保留；撤回退时它随代码一起同步更新。

构建型插件：源码与产物同名

前面以源码直载为例（entry 指向 server/main.ts）。需要打包的插件——用 Bun 打包、 或带非 JS 资源——必须满足同一个入口形状：

位置server 入口
源码（包根）server/main.ts
构建产物dist/server/main.js
ocplugin.json（两处都用这一份）"entry": { "server": "server/main" }

包根与 dist/ 共用一份 ocplugin.json：宿主在包根按 .ts 命中源码， 在解包目录按 .js 命中产物，entry 不用改。所以构建输出必须命名成 main.js， 不能沿用旧的 index.js。 

script/build.ts（片段）const build = await Bun.build({
  entrypoints: [join(root, "server", "main.ts")],
  target: "bun",
  format: "esm",
  outdir: join(dist, "server"),
  naming: "main.js",                 // → dist/server/main.js
  external: [...manifest.externals, "node:*"],
})

dist/package.json 的 main / exports 同样指向 ./server/main.js。打包时把 ocplugin.json 原样拷进 dist/，不改写 entry。

packages/plugins/webwright 就是这种形态：server/main.ts 构建成 dist/server/main.js，entry.server 始终是 server/main。 packages/plugins/figma 是源码直载的样本，没有构建步骤。

旧布局已废弃（源码在 src/index.ts、entry.server 写 server/index.js）。 仓库内的插件都已迁到 server/main；回退分支只为仓库外尚未迁移的插件保留， 每次加载都会打警告，见上一小节。

2.1 插件运行时（Python）

依赖 Python 的插件在清单里声明运行时与依赖。平台为每个插件准备一个独立环境， 不写系统 site-packages，不改全局环境。 

ocplugin.json"runtime": {
  "python": ">=3.10",
  "dependencies": ["pymysql>=1.0", "psycopg2-binary>=2.9"]
}

python 与 dependencies 都可选。目前只实现 Python，字段结构预留给以后的其他运行时。

环境位置

项说明
目录（macOS / Linux）~/.opencode/plugin-runtime/<id>/，id 里的 / 换成 +。
目录（Windows） D:\.opencode\plugin-runtime\<id>\；D:\ 不存在或不可写时回落 %USERPROFILE%\.opencode\plugin-runtime\<id>\。判定细节见目录位置。
卸载时整个目录删除。它是可重建的，与 plugin-cache 同一类。
标记文件环境目录里的 runtime.json 记录约束与依赖的 hash、解释器版本和准备时间。

目录位置（Windows 默认放 D 盘）

宿主给每个插件四个目录，只有可重建的两项会挪到别的盘：运行环境与缓存。 数据与日志始终留在用户主目录，所以掉盘最多损失一次重新准备，不会丢配置和日志。

目录macOS / LinuxWindows
运行环境 ~/.opencode/plugin-runtime/<id>/ D:\.opencode\plugin-runtime\<id>\，否则 %USERPROFILE%\.opencode\plugin-runtime\<id>\
缓存 ~/.opencode/plugin-cache/<id>/ D:\.opencode\plugin-cache\<id>\，否则 %USERPROFILE%\.opencode\plugin-cache\<id>\
数据（config.json） ~/.opencode/plugin-data/<id>/ %USERPROFILE%\.opencode\plugin-data\<id>\
日志 ~/.opencode/logs/plugin/<id>.log %USERPROFILE%\.opencode\logs\plugin\<id>.log

判定条件是 D:\ 存在且可写（accessSync("D:\\", W_OK)）：只读盘、光驱不会被采用。 非 Windows 平台不看这个条件，四个目录都在 ~/.opencode 下，行为与之前完全相同。 ~/.opencode/ocplugins、~/.ocplugins-local、secrets/、secrets.key 的位置也没有变化。

换盘之后

  • 新环境 ready 之后，旧根下的 plugin-cache 与 plugin-runtime 会被删除。
  • plugin-data 与 logs/plugin 不动——它们本来就不随盘移动。
  • 准备失败时旧环境保留，不清理，避免把还能用的环境删掉。

探测结果在进程内只取一次（列表、卸载、配置扫描都会问路径，不能每次都发 syscall）， 所以换盘或插拔盘之后要重启 OpenCode 才会重新判定。

已知代价：外接盘或网络盘掉线时，本次进程仍按启动时的判定继续用 D:\，准备可能因此失败； 重启后判定为不可用，回落到 C 盘重新准备一次。盘接回来再启动，又会在 D:\ 上准备一次，每次几十秒。 这是有意的取舍——这里不加锁、不做健康检查，也故意不在每次调用时重探（那样会把真实的存储问题 悄悄搬回主目录），否则问题会被掩盖而不是报出来，所以不要把它当成 bug。

检测与准备

每次加载都会检测三项，任一项不过就重新准备：

  1. 虚拟环境存在且解释器可用。
  2. 解释器版本满足 runtime.python。约束里的运算符（>=、^、~）只用来取最低版本，比较时只校验下限，与 requires.opencode 的判定方式相同。
  3. 依赖规范化后的 hash 与标记文件一致。
  • 解释器优先用 uv：uv venv --python <最低版本>。机器上没有 uv 时，宿主会自己下载一份（见下节）；连下载都不可用才回退系统 python3（-m venv），并先校验版本。
  • 依赖安装：有 uv 用 uv pip install，否则用 python -m pip install。
  • 两者都不满足 → failed，错误信息包含所需版本、实际版本与 uv 不可用的原因。 失败不会自动重试。

uv 与镜像（国内优先）

用户不需要先装 uv：机器上没有时，宿主会下载一份可执行的 uv， 并且默认全部走国内镜像，不让首次准备卡在访问 GitHub 上。

找 uv 的顺序

  1. OPENCODE_UV_PATH 指定的路径，能跑就用。
  2. PATH 里的 uv。
  3. 已经下载过、能跑的 ~/.opencode/bin/uv。
  4. 都没有才下载。

下载源（三级回退，国内优先）

  1. 中科大 GitHub release 镜像：https://mirrors.ustc.edu.cn/github-release/astral-sh/uv/<version>/<asset>
  2. 代理：https://gh-proxy.com/https://github.com/astral-sh/uv/releases/download/<version>/<asset>
  3. 官方 GitHub：https://github.com/astral-sh/uv/releases/download/<version>/<asset>

每一级失败静默进下一级；三级都失败才回退系统 python3， 错误信息按源列出各自的原因（带主机名）。

版本与平台

项规则
版本固定 0.13.8，不跟 latest——一个代码版本对应一份工具链，环境可复现。用 OPENCODE_UV_VERSION 覆盖。
平台darwin-arm64、darwin-x64、linux-arm64、linux-x64、win32-x64。其余组合 uv 没有可用构建，直接回退系统 python3。
包格式macOS / Linux 是 .tar.gz；Windows 是 .zip。
解压Bun.Archive 只读 tar，所以 Windows 的 zip 由宿主自己读中央目录、用 inflateRawSync 取出 uv.exe。
校验和源提供 <asset>.sha256 就校验，不匹配算本级失败；不提供就跳过。宿主不维护硬编码的 sha256 表。
幂等与并发~/.opencode/bin/uv 能跑就不重复下载；先解压到临时目录，再 rename 原子落盘，两个插件同时准备也只下载一次。
下载后自检落盘后会实际执行一次 uv --version，跑不起来算本级失败，不会留下一个不能 spawn 的路径。

用途变量
uv venv 取 CPython 的来源UV_PYTHON_INSTALL_MIRROR
uv 的包索引UV_DEFAULT_INDEX 与 UV_INDEX_URL（同值，兼容旧版 uv）
系统 pip 的包索引PIP_INDEX_URL

默认全部指向中科大，可用这些变量覆盖：

OPENCODE_UV_MIRROR换 uv 下载镜像；设成空字符串则跳过镜像，只用代理与官方。

下载并执行 uv 与「安装插件声明的依赖」是同一层信任：用户装了一个声明 runtime 的插件， 就等于同意宿主在需要时取一次解释器工具链。仍然不写系统 site-packages。

状态与通知

Plugin.Info.runtime含义
{ status: "preparing" } 正在准备，但还没上报阶段。这个形态只存在于「进入准备」到「首次上报」之间：phase 在 prepare 的第一行就发，早于 uv 探测与下载。
{ status: "preparing", phase: "runtime" }正在准备运行时：取 uv、建虚拟环境、下载 Python。
{ status: "preparing", phase: "dependencies" }正在安装依赖：uv pip install 或 pip install。
{ status: "ready" }可用。
{ status: "failed", error, ref }失败；error 是原因，ref 对应服务端的一条日志。

phase 是可选的 "runtime" | "dependencies"，只在 preparing 时存在： ready 与 failed 没有可报的阶段，不带这个字段。没有依赖要装时不会出现 dependencies 阶段，准备完直接跳到 ready。

未声明 runtime 的插件没有这个字段。状态变化通过 Plugin.Event.Updated 通知客户端， 与插件列表的其他变化走同一条推送；phase 变化也会立即推一次，不用等整个准备结束。

异步，不阻塞安装

  • 安装接口立即返回，环境在后台准备：preparing → ready / failed。
  • 环境失败不等于插件失败：插件保留、仍可加载，只是依赖它的功能用不了。
  • 加载已有插件时也会检测，所以「先装好、之后才在清单里加 runtime」的场景会自动补装，不用重装插件。

失败后重新准备

准备失败不会自动重试。修好环境（装 uv、装合适版本的 Python，或让宿主能访问镜像）后调端点，或点界面上的「重新准备」：

方法 / 路径请求响应
POST /api/experimental/plugin/runtime/retry query LocationQuery；body { "id": "<plugin id>" } 200 { id }；404 PluginNotFoundError（id 不在 inventory，或该插件没有声明 runtime）

它只重新准备环境，不重载插件；要重载插件用 3.4 的 plugin.reload。 回复 200 只表示已开始准备，进度通过插件 inventory 的 runtime.status 观察。

界面表现

  • 插件详情页有「运行环境」一项：正在准备 / 已就绪 / 准备失败。 正在准备时还会显示当前阶段——「正在准备运行时」（Preparing runtime）或 「正在安装依赖」（Installing dependencies）。ready 与 failed 不显示阶段。
  • 阶段在最开头就上报，早于 uv 探测与下载。所以第一次安装、机器上还没有 uv 时， 下载期间界面已经显示「正在准备运行时」，不会长时间停在无阶段的「正在准备」上。 uv 探测失败而回退系统 python3 时，报的也是当时正在做的阶段。
  • 失败时显示错误（复用插件失败的样式）与「重新准备」按钮。
  • 安装成功且插件声明了 runtime 时，追加一条 toast「正在为 … 准备运行环境」，不阻塞安装对话框。
  • 未声明 runtime 的插件不显示这一项。

安全边界

pip install 会执行依赖包里的构建步骤（包括 setup.py），等于在用户机器上运行代码。 这属于既有的「插件完全信任」模型：插件本来就能读写文件、启动进程、访问网络。 平台做的是「把依赖装进隔离目录」，不是沙箱——不要以为运行时准备提供了额外的安全隔离。

还没声明 runtime 的插件

dbro 这类现有插件目前自己解决解释器：用 configuration.python（默认 python3）指向可执行文件， 再用 Bun.spawn 调用脚本，找不到时提示「找不到 Python 解释器「…」。安装 python3，或在插件设置里把 python 指向可执行文件。」。 迁移到 runtime 后，这一步由平台负责。

3.1 包格式

.ocplugin 是 gzip 压缩的 tar 包。根目录必须有 ocplugin.json，且清单里带 files 校验和。 

opencode.echo-0.1.0.ocplugin  (gzip tar)

3.2 script/pack.ts

echo-plugin/script/pack.tsimport { createHash } from "node:crypto"
import { mkdir, readdir, readFile } from "node:fs/promises"
import { homedir } from "node:os"
import { join, relative, sep } from "node:path"

const root = join(import.meta.dir, "..")
const dist = join(root, "dist")
const manifest = await Bun.file(join(root, "ocplugin.json")).json()

async function walk(directory: string): Promise<string[]> {
  const entries = await readdir(directory, { withFileTypes: true })
  const nested = await Promise.all(
    entries.map((entry) => {
      const full = join(directory, entry.name)
      return entry.isDirectory() ? walk(full) : [full]
    }),
  )
  return nested.flat()
}

const paths = (await walk(dist))
  .map((file) => relative(dist, file).split(sep).join("/"))
  .filter((path) => path !== "ocplugin.json")
  .sort()

const files: Record<string, Uint8Array> = {}
const checks: { path: string; sha256: string }[] = []

for (const path of paths) {
  const bytes = new Uint8Array(await readFile(join(dist, ...path.split("/"))))
  files[path] = bytes
  checks.push({ path, sha256: createHash("sha256").update(bytes).digest("hex") })
}

files["ocplugin.json"] = new TextEncoder().encode(
  JSON.stringify({ ...manifest, files: checks }, null, 2) + "\n",
)

const out = join(homedir(), ".ocplugins-local", manifest.id, manifest.version)
await mkdir(out, { recursive: true })

const archive = join(out, `${manifest.id}-${manifest.version}.ocplugin`)
await Bun.Archive.write(archive, files, { compress: "gzip", level: 9 })

// 插件目录读取的侧车清单，不必解压
await Bun.write(join(out, "manifest.json"), JSON.stringify(manifest, null, 2) + "\n")

console.log(`packed ${archive}`)

3.3 打包规则

规则 说明
文件清单 dist/ 下所有普通文件，路径用 / 分隔。
清单重写 包根 ocplugin.json 由打包脚本重写，包含 files[].sha256。
自引用 ocplugin.json 不列入 files，避免循环。
输出位置 ~/.ocplugins-local/<id>/<version>/<id>-<version>.ocplugin。
侧车清单 同目录 manifest.json（不含 files），供插件目录快速读取。
压缩 gzip，压缩级别 9。
确定性 Bun.Archive 写入当前时间戳，两次打包 sha256 不同。需要可复现构建请手写 tar 头（见 3.6）。

3.4 安装与自动加载

  1. 放入待安装目录

    把 .ocplugin 放到 ~/.ocplugins-local/<id>/<version>/。

  2. 在应用中安装

    打开 Explore 页的插件列表，找到该条目，点安装。

  3. 安装器校验

    • apiVersion === 1
    • 清单 id 与请求 id 一致
    • 版本一致（若指定）
    • 每个 files[].sha256 匹配

  4. 解包

    解包到 ~/.opencode/ocplugins/<id>/，并按 externals 把宿主模块软链进插件的 node_modules。

  5. 自动加载

    安装根目录被监听，文件变化触发重新加载：服务端重新执行 activate，广播 plugin.updated，桌面主进程把界面推给窗口。全程不需要重启应用。

加载超时、退避与显式重试

加载不再无限等待，失败后也不会被反复重试打死：

  • 服务端单次加载超时 15 秒，超时按普通加载失败处理并进入退避。计时只覆盖 npm 安装/解析与模块导入， 读配置和 GUI bundle 不在其内。桌面端加载插件主代码同样是 15 秒，超时后不保留半启动的实例。
  • 连续失败按 min(2^count × 1000ms, 60s) 递推退避；退避窗口内同一目标不再被解析或导入， 直接沿用上一次的失败结果。加载成功、配置项变化、显式重试都会把计数清零。退避只在进程内，重启应用后重新尝试。
  • 带 install 的包安装不再阻塞激活：本地插件先服务，安装在后台完成后才并入注册表。

插件连续失败进入退避窗口后，修好代码（或重新安装）不必等窗口过期，调下面这个端点即可立即重试：

方法 / 路径请求响应
POST /api/experimental/plugin/reload query LocationQuery；body { "id": "<plugin id>" } 200 { location, data: { id } }；
404 PluginNotFoundError（id 不在当前 location 的插件清单里） 
HTTPPOST /api/experimental/plugin/reload
Content-Type: application/json

{ "id": "opencode.echo" }

语义是「清掉该目标的加载退避，再通过 supervisor 既有的触发队列请求一次重新激活」，不会另起一条激活链。 返回 200 只表示已排入重试，不表示插件已经加载成功：要看插件状态，读 GET /api/plugin 里的 state.status。

客户端对应 client.experimental.plugin.reload({ id })。桌面端的插件详情页在 state.status === "failed" 且来源不是 builtin 时显示「重试」按钮， 请求期间按钮禁用并显示「正在重试…」，失败信息显示在按钮下方。

这是实验性端点，可能在没有兼容保证的情况下变化。同类实验性路由（install、uninstall、 check）在 OpenAPI 的 plugin 分组下。

activate 的超时保护（30 秒）

服务端执行 activate 时挂一个 30 秒的可中断挂起的超时保护。 它不是「修复插件挂死」的通用药：只对能被中断的等待有效，越界的情形要提前知道。

activate 里的写法30 秒后
Effect.never、Effect.sleep 等可中断挂起 被中断，插件标记为失败。
Effect.promise(() => new Promise(() => {})) 这类不可中断的 promise 不会被中断，超时对它不起作用。
同步死循环 不会被中断：它阻塞事件循环，任何 timeout 都无法触发。 这类代码要放到 worker 或独立进程里，该隔离尚未实现。

超时后插件进入 failed，带 reason: { kind: "activation-timeout", seconds: 30 } 与 ref: err_xxxxxxxx。它不进入 supervisor 的退避队列——退避是挡「反复失败」的， 而超时的插件本身没坏，只是慢。要再次激活，得改它的 revision（重新安装、改配置或显式重载）。 激活是顺序进行的，语义不变：一个插件超时，后面的插件照常激活。

为什么是 30 秒、且没有配置项：在 activate 里探测端口、拉远端配置的插件， 合法地超过 10 秒很常见。10 秒一刀切会把「慢」误判成「坏」，停掉一个其实正常的插件。 30 秒是硬编码的折中；一旦开放配置，每个插件都会把它调大，保护也就失去意义。

失败状态的结构（state.failed）

failed 由三段组成：error（服务端原始详情，英文堆栈）、可选的 ref（err_xxxxxxxx，对应日志）、可选的 reason（结构化原因）。 面向用户的部分读 reason：界面按它做本地化，原始 error 只出现在折叠详情里。

Plugin.Reason含义
{ kind: "transform-failed", state } 某个状态域（如 server）在重建时抛错，该组注册被回滚，插件被停用。
{ kind: "activation-timeout", seconds } activate 超过 30 秒，见上一小节。
{ kind: "load-timeout", seconds } 模块加载与解析超过 15 秒，见上文。
{ kind: "load-failed" } 其余加载失败。

界面文案键在 packages/app/src/runtime/i18n/{en,zh,zht}.ts： explore.plugins.error.reason.transformFailed（{{state}}）、 explore.plugins.error.reason.activationTimeout（{{seconds}}）、 explore.plugins.error.reason.loadTimeout（{{seconds}}）、 explore.plugins.error.reason.loadFailed。 旧的 .reason.transform / .timeout / .load 已改名删除。

加密凭据（ctx.secrets）

服务端await ctx.secrets.set("token", apiKey)
const token = await ctx.secrets.get("token")   // string | undefined
await ctx.secrets.delete("token")

值用 AES-256-GCM 加密后写入 ~/.opencode/secrets/<id>.json，文件权限 0600； 密钥在 ~/.opencode/secrets.key，首次使用时生成，权限同样是 0600， 已存在时不会覆盖。明文从不落盘。

  • 同一个 key 再次 set 是覆盖写，不保留旧值。
  • delete 一个不存在的 key 是 no-op，不报错。
  • secrets.key 已存在时不会覆盖；两个进程同时首次生成时以先落盘者为准，后写的进程沿用对方生成的密钥。
这套加密防的是误提交、误上传和明文备份泄漏，防不了已经拿到本机读权限的人： 密钥和密文在同一台机器上，能读文件就能解密。不要把它当成对抗本地攻击者的边界。

声明式配置（ctx.config）

清单的 configuration 声明一组扁平配置项，宿主据此校验和读写 <ctx.paths.data>/config.json。 

ocplugin.json"configuration": {
  "title": "ACME 设置",
  "properties": {
    "endpoint": { "type": "string", "default": "" },
    "timeout": { "type": "number", "default": 30 },
    "mode": { "type": "string", "enum": ["ro", "rw"], "default": "ro" },
    "sources": { "type": "array", "items": { "type": "string" }, "default": [] }
  }
}
服务端const config = await ctx.config.get()          // 已合并 default，未声明的键被裁掉
await ctx.config.update({ timeout: 60 })       // 校验类型后写文件，再通知监听者
ctx.config.onChange((next) => { ... })         // 随插件 scope 关闭自动移除
  • type 只能是 string、number、boolean、array；不支持嵌套对象和对象数组。
  • enum 只能配在 string 上；array 只支持 items.type 为 "string"。
  • 这里是用户级、运行时可变的配置，不会与 opencode.json 里给插件的 options 合并：options 是静态的、随项目提交的。
  • 宿主不会按清单自动渲染设置页。插件仍自己 ctx.add(SettingsPage)，需要时通过自定义 RPC 调服务端的 ctx.config.update。
  • 运行时错误文案固定为 Unknown configuration key: <name> 与 Invalid configuration value for <name>，插件可以按这两条判断失败原因。
  • 多个 onChange 监听者的通知顺序不保证，不要依赖注册顺序。

4.14 声明（Declarations）

Plugin.define 除 id / setup / main 外，还有一组声明： os、i18n、stores。宿主在任何 setup 执行之前读取它们， 所以声明里不能引用运行时才知道的值。 

gui/main.tsxexport default Plugin.define({
  os: ["macos", "windows"],
  i18n: { en: { title: "Acme" }, "zh-CN": { title: "Acme 工具" } },
  stores: {
    prefs: Store.global(Prefs, { shown: true }, "plugin.acme.settings"),
    view: Store.session(View, { open: [] }),
  },
  setup(ctx) {
    const shown = () => ctx.stores.prefs.value.shown
    const open = (session) => ctx.stores.view(session).value?.open ?? []
  },
})

os

值含义
"macos"macOS。
"windows"Windows。
"linux"Linux 及其他桌面平台。

省略表示全平台。从配置安装的插件只在桌面版运行；内置插件若列出了任一 OS，则在 Web 端不运行 （Web 端没有可判断的 OS）。

  • 英文必填，同时作为其他语言缺失键的兜底。
  • 插值写 {{name}}，由 ctx.t(key, { name }) 填充。
  • 复数键带 CLDR 后缀，如 files.one / files.other，用 ctx.plural("files", 3) 读取；{{count}} 自动填入。

ctx.t 的回退链：先查插件字典，再交给应用的语言模块解析共享键（如 common.*）。 ctx.plural 则先读 <key>.<category>，再读 <key>.other。

用 Store.global 或 Store.session 声明。键名就是 ctx.stores 上的属性名， 实际存储键是 plugin.<id>.<name>。

工厂作用域读取
Store.global(schema, initial, from?) 整个应用一份，setup 之前加载完成 ctx.stores.prefs.value，永不为 undefined
Store.session(schema, initial, from?) 每个会话一份，会话挂载时开始加载 ctx.stores.view(session).value，加载完成前与位置未知时为 undefined

schema 必须是对象 schema。字段缺失或解码失败时取 initial； 整体解码失败时读作 initial。

from 是一次性的旧键迁移：只在该 store 还没有值时导入，可以是单个键或「从新到旧」的列表 （第一个有值的被导入）。例如 Store.global(Prefs, { shown: true }, "plugin.acme.settings")。 旧键会保留自己的副本，直到用 ctx.storage.remove 连 from 一起删除。

成员说明
value存储值；窗口里是响应式的，加载完成前为 undefined（global store 例外）。
ready()是否已加载；主进程里恒为 true。
update(draft => undefined)在深可变草稿上原地修改；不能返回替代值。
set(next)整体替换，用于原始类型或替换整个对象。

三套存储的差别

位置接口同步说明
服务端 ctx.storage get、set、remove、scan 否（Promise） 值必须是 Schema.Json，即纯 JSON。
GUI 窗口 ctx.storage store(key, { schema, initial, scope, from })、memory(key, { initial })、remove(key, { scope, from }) 否（响应式） 给运行时才知道的键用（例如按服务器与目录生成的键）。memory 只活在当前窗口，插件重载后仍在，窗口重载后丢失。
GUI 窗口 ctx.stores 声明式，见上 否（响应式） 键在定义时就已知时优先用它，宿主负责在读取前加载。
主进程 ctx.storage store(key, options)、remove(key) 是 同步读写，跨窗口共享；主进程没有声明式 stores。

生命周期钩子

服务端插件用声明式方法描述生命周期，由宿主按确定规则调用。三个钩子都可选；都不写时行为与从前一致。 

服务端export default Plugin.define({
  id: "opencode.acme",

  async activate(ctx) {},     // 每次加载都跑；旧名 setup
  async onInstall(ctx) {},    // 本进程内首次加载
  async onUninstall(ctx) {},  // 卸载，删目录之前，运行中的旧实例
})
钩子触发时机接收者
activate（旧名 setup）每次加载新实例
onInstall本进程内首次加载新实例
onUninstall卸载，插件目录删除之前运行中的旧实例

判定规则：

  • 首次加载：onInstall → activate。
  • 同 id、revision 不变：什么都不跑。
  • 同 id、revision 变化：旧实例 onCleanup → 新实例 activate，不触发 onInstall，也不触发 onUninstall。
  • 停用后重新启用：只跑 activate，不触发 onInstall。
  • onInstall / onUninstall 最多 3 秒，抛错只记 warning，不阻塞加载或卸载。 activate 是 30 秒，且只对可中断挂起有效，见 3.4 的 activate 超时保护。
  • 已停用的插件不跑 onUninstall，也不会为了跑它而临时加载。
  • onInstall 是本进程内的判定：重启后会再触发一次，实现必须幂等。
  • 没有 onReload 钩子：重载就是「旧实例 cleanup + 新实例 activate」，与 VSCode 的语义一致。需要跨重载保留的状态放 ctx.paths.data 或 ctx.storage，不要指望一个重载专用回调。
  • 桌面界面入口不提供这三个钩子；界面侧只有 setup / main。

4.18 收件箱（ctx.inbox）

ctx.inbox 让服务端插件往应用的收件箱里投递「给用户看的事项」：一条待审的评审请求、 一个待填的表单、一次后台任务的结果。它只存在于服务端 Context；GUI 窗口的 ctx 没有 inbox。 

服务端const id = await ctx.inbox.publish({
  externalID: "pull-42",                    // 插件自己的消息 id
  title: "新的评审请求",
  summary: "仓库 acme/api 的 #42 需要你审一次",
  status: "pending",
  payload: { repo: "acme/api", number: 42 },
})

await ctx.inbox.publishMany([{ externalID: "a", title: "A", summary: "…" }])

const records = await ctx.inbox.list()      // 只有本插件投递的消息
await ctx.inbox.update(id, { status: "done" })
await ctx.inbox.markSeen(id)
await ctx.inbox.remove(id)

ctx.inbox.onSeen((ids) => {                // 用户把本插件的消息标记为已读
  console.log(ids)
})
成员签名说明
publish(message: InboxMessage) => Promise<InboxID>投递一条；同一 externalID 再投递是更新而不是新增。
publishMany(messages: InboxMessage[]) => Promise<InboxID[]>批量投递，返回与输入同序的 id。
list() => Promise<InboxRecord[]>只返回本插件投递的消息。每条的 createdAt 一定存在，但不含 plugin 字段（平台端点与界面侧才有，见下文）。不保证按时间排序，顺序与存储扫描顺序一致。
update(id: InboxID, patch: InboxPatch) => Promise<void>只改 title、summary、status、expiresAt、payload。expiresAt: null 清除截止时间；externalID 与 createdAt 不会被改。
remove(id: InboxID) => Promise<void>硬删除记录与索引。删后用同一个 externalID 再 publish，会生成新的 id。插件只能删自己的；用户随时可以删任意插件的一条（见下文「消息不是永久的」）。
markSeen(id: InboxID) => Promise<void>把消息标记为已读。不触发自己的 onSeen：那是用户的动作才算数。已经是已读时是 no-op，不刷新 updatedAt。
onSeen(callback: (ids: InboxID[]) => void) => void用户把本插件的消息读掉（例如在收件箱里打开一条）时回调，参数是那次操作读到的 id。回调抛错只记日志，不影响标记请求。监听者随插件实例一起释放。

类型

@opencode/plugintype InboxStatus = "pending" | "done" | "failed"

type InboxMessage = {
  externalID: string        // 同插件内重复投递按更新处理
  title: string
  summary: string
  status?: InboxStatus      // 默认 "pending"
  createdAt?: number        // 默认投递时间
  expiresAt?: number
  payload?: unknown
}

type InboxRecord = InboxMessage & {
  id: InboxID
  seen: boolean
  updatedAt: number
}

type InboxPatch = {
  title?: string
  summary?: string
  status?: InboxStatus
  expiresAt?: number | null
  payload?: unknown
}

三种途径拿到的 record 略有差别：

途径是否含 plugin
ctx.inbox.list()否。只有本插件的消息，发布者不言自明；createdAt 一定存在。
GET /api/experimental/plugin/inbox是。一次返回该 location 里所有插件投递的消息，需要 plugin 区分来源；按 createdAt 降序（最新在前）。
InboxContent.render(record)是。宿主用 record.plugin 把消息路由到发布者的渲染器。

payload 对平台是不透明的，但它会存进 JSON 存储，必须能走一遍 JSON.stringify： 循环引用、BigInt、函数这类值在投递时就会出错。

行为

行为说明
完全隔离 list() 只返回本插件投递的消息；对不属于自己的 id 做 update / remove / markSeen 静默无效，不报错。
幂等 同一 externalID 重复投递是更新，不新增记录。更新不覆盖 status、seen 与 createdAt；payload / expiresAt 传了新值就覆盖，没传则保留旧值。
两个独立维度 status 由插件控制，seen 由用户控制。插件改不动 seen，用户也改不动 status。
持久化与多端共享 记录存在服务端该 location 的数据库里，不是某个窗口的内存。多个窗口与多个客户端读同一份记录和已读状态， 在一个窗口标记已读，另一个窗口刷新后也是已读。
remove 是硬删除 从存储中删掉记录与索引，删后不在列表、也不在历史；用同一个 externalID 再 publish 会生成新的 id。没有「已撤回」状态、软删标记或墓碑。
历史不自动清理 宿主不设 TTL。插件不再投递、但用户处理过的消息会留在历史里，只有用户手动删除或插件显式 remove 才会消失。
没有全局 markAll 插件只能 markSeen(id)，没有「把本插件全部标记已读」的接口。

平台端点（给应用与客户端用）

插件自己不调这些端点：ctx.inbox 就是它们的插件侧封装。它们由桌面应用与客户端使用， 都属于实验性路由。

方法 / 路径请求响应
GET /api/experimental/plugin/inbox query LocationQuery 200，该 location 里所有插件投递的消息，每条含 plugin，按 createdAt 降序；应用据此展示跨插件的统一列表。
POST /api/experimental/plugin/inbox/mark query LocationQuery；body { "id": "<InboxID>" } 204 无内容。未知 id 是 no-op。
POST /api/experimental/plugin/inbox/delete query LocationQuery；body { "id": "<InboxID>" } 204 无内容。一次删掉一条消息的三个 KV 键（见下），未知 id 是 no-op，重复删除安全。 这是用户的清理入口，不限于某个插件。

OpenAPI identifier 分别是 experimental.plugin.inbox.list、 experimental.plugin.inbox.mark 与 experimental.plugin.inbox.delete。 mark 代表用户把一条消息标记为已读， 所以会触发发布者的 ctx.inbox.onSeen；已经读过的 id 不会重复通知。 delete 则不产生任何回调，插件只能靠 list() 感知。

消息不是永久的：用户可随时删除

收件箱是用户的列表，不是插件的存储。用户能在详情页把任意一条插件消息直接删掉，不论它来自哪个插件。 插件必须按这个前提写：

  • 不得假设自己投递过的消息仍然存在；ctx.inbox.list() 是唯一事实来源， 需要时重新读，不要缓存一份旧的当作真相。
  • 平台不保证「删了别再来」：用同一个 externalID 重新投递会生成一条新消息， 被删的记录不留墓碑。要「只提醒一次」的插件，得在自己的 ctx.storage 或 ctx.paths.data 里记录提醒过什么，而不是指望收件箱记住。
  • 删除没有事件。没有 onRemoved 之类的回调，插件通过 list() 或用户下一次交互发现消息消失。

plugin.inbox.delete 最终调用 PluginInbox.remove：一条消息在 KV 里是三个键 （packages/core/src/plugin/inbox.ts），硬删除时三个一起删。

键作用
plugin-inbox:msg:<plugin>:<id>消息本体（record）。
plugin-inbox:ext:<plugin>:<externalID>externalID 索引，让重投成为更新。
plugin-inbox:own:<id>owner 索引，让应用在不知道发布者时也能标记已读、删除。

<plugin> 与 <externalID> 在键里按每个字符 4 位十六进制转义， 避免分隔符产生歧义。三个键不是一个事务：写入中途崩溃可能留下没有 record 的索引，读取时按缺失处理。 没有墓碑，所以同一个 externalID 之后重投得到的是一条全新消息，而不是「复活」旧记录。

内容页渲染

导航区（侧边栏列表、过滤、搜索、未读点与排序）由宿主渲染，插件不能改。插件能自定义的是单条消息的内容页， 而且只对自己的消息生效。 

guiimport { InboxContent } from "@opencode/plugin/gui"

ctx.add(InboxContent, {
  render: (record) => <MailMessage id={record.id} payload={record.payload} />,
})

render 收到的 record 比服务端的 InboxRecord 多一个 plugin 字段（发布者的插件 id），其余字段一致。返回 undefined 表示这一条继续用宿主默认页； 渲染抛错时该页渲染为空并记录错误。页面自身的响应式更新要自己负责。

内容页底部还有一条宿主操作条，其中的「删除消息」由宿主提供，位于插件自定义渲染之外： 插件有没有自带页面，用户都能删掉这条消息。文案键是 inbox.detail.action.deleteMessage；它与本地历史记录的 inbox.detail.action.delete（「Delete from history」）不是一回事，后者只删本地的历史条目。 删除后 ctx.inbox.list() 与应用的收件箱都不再包含该条。

默认内容页与已读

没注册渲染器（或 render 返回 undefined）时走宿主默认页：显示标题、摘要、来源插件、 状态与创建时间，不显示 payload——要展示 payload 就自己注册 InboxContent。

列表每一行的图标由宿主按 status 选：pending → output、done → result、 failed → failure。图标只反映状态，不改变排序或过滤。

打开一条插件消息即视为已读：应用会调 POST /api/experimental/plugin/inbox/mark， 服务端写入 seen 并触发发布者的 onSeen；刷新后与多窗口看到的状态一致。

收件箱列表的顺序由宿主决定：按 createdAt 降序，最新的在前。 插件侧 ctx.inbox.list() 目前不排序，顺序与 KV 扫描一致；需要特定顺序就自己排。

已知差距（后续批次）：插件侧 ctx.inbox.list() 尚未按时间排序， 计划在下个 minor 与宿主列表统一为此处的降序。在那之前不要把它的返回顺序当作时间顺序。

它不是会话消息队列

session_inbox 是会话的投递队列：用户消息的排队、steer / queue 两种投递方式、附件与合成消息都在那里，归会话运行时所有，插件不该碰。收件箱（本节）是给用户看的事项列表， 与某个会话的执行顺序无关。两者名字相近，别混用。

5.1 确认插件被加载

在 activate 开头写一行日志：

server/main.tsexport default Plugin.define({

  },

覆盖安装目录后看服务端日志。没有这一行说明插件没有被发现或加载失败。

5.2 确认界面被加载

  1. 插件处于启用状态。
  2. ocplugin.json 的 entry.gui 是 gui/main，产物是 gui/main.cjs 或 gui/main.js。
  3. bundle 是 CommonJS，不含 import/export 语句。
  4. 在桌面端运行；Web 端不加载第三方界面。

5.3 确认工具被调用

  1. 让模型「列出可用工具」，看工具名是否出现。
  2. 直接要求调用，观察时间线里的参数与结果。
  3. 输入 Schema 不匹配时，模型会收到校验错误并可能自行重试。

5.4 热更新不生效

  1. 确认覆盖的是 ~/.opencode/ocplugins/<id>/，不是项目里的 dist/。
  2. 确认构建产物时间戳已更新。
  3. 手动触碰目录：touch ~/.opencode/ocplugins/<id>。

如果插件已经进入加载失败后的退避窗口，改文件不会立刻重试：见 3.4「加载超时、退避与显式重试」，用重试端点或插件详情页的「重试」按钮立即恢复。 若原因是 activate 超时（reason.kind === "activation-timeout"），它本来就不进退避， 改文件或点「重试」都会重新激活，见 3.4 的 activate 超时保护。

8. 能力边界与常见问题

能力边界

下面是「能不能做桌面级能力」这个问题的准确答案，按代价从低到高排列。

一、只差公开暴露（内部已实现）

能力现状
已有窗口的读取与事件 ctx.windows.get/list/focused/on 已公开，是唯一受支持的窗口入口。
页面嵌入 ctx.embeds.create(view, window) 把 WebContentsView 放进已有窗口布局。
显示器信息 主进程内部已有 screen.getAllDisplays 等封装（窗口状态恢复在用），尚未作为 ctx 成员公开。

二、需要新增受管实现

这些能力本身在 Electron 里存在，主进程 bundle 也能 require("electron")，缺的是公开 API、 生命周期绑定和权限声明。不做这些，插件只能走非公开路径，插件重载或停用后资源会残留。

能力缺什么
Overlay 窗口（透明、无框、置顶、穿透）创建 API、渲染入口、窗口类型标记、与插件实例绑定的销毁。
托盘图标创建、菜单、点击事件；仓库里没有现成的 Tray 封装。
全局快捷键注册、冲突检测、按插件隔离与自动释放；仓库里没有 globalShortcut 封装。
开机自启该设置属于整个应用，多插件会互相覆盖，需要宿主合并后才能公开。

三、需要改架构

补 overlay 前必须先解决，否则会污染主窗口的恢复与退出语义：

  • 事件广播目前只发给注册的主窗口，overlay 窗口收不到插件事件。
  • 渲染入口没有窗口类型分支，overlay 需要与主窗口共用同一份 renderer bundle，靠启动参数区分。
  • window-all-closed 与 activate 会把 overlay 当成主窗口，导致「还有窗口就不退出」的错误判断。

四、明确不做

  • 把 BrowserWindow 或 webContents 实例直接交给插件：无法撤销，插件重载后窗口残留。
  • 为插件新增独立 HTML 入口：插件 bundle 的求值依赖应用的模块白名单，独立入口会绕开它。
  • 清单字段 entry.gui / entry.tui / entry.rpc 的自动消费：当前安装器只读 entry.server，写这些字段不会产生任何效果。

卸载回调的边界

onUninstall 钩子（见 4.14）有这些限制：

  • 只有运行中的插件会收到。已停用的插件没有活动实例，调用卸载时直接跳过，不会为了执行回调而临时加载插件代码。
  • 重载（插件 revision 变化）、停用（配置变化）与进程退出都不触发它，只走正常的 scope 关闭与 ctx.onCleanup。
  • 只在被卸载时触发；onInstall 是本进程内的判定，重启后会再触发一次，实现必须幂等。
  • 每个钩子最多 3 秒；超时记 warning 并继续删除，钩子抛错也不阻塞卸载。
  • 卸载时宿主删 ctx.paths.cache，保留 ctx.paths.data 与 ctx.paths.log；需要清理就在这个钩子里自己做。
  • 第一版只覆盖服务端入口。桌面端的插件重载逻辑只知道插件从列表消失，分不清「卸载」与「停用」，贸然触发会在用户停用插件时删掉数据，所以 GUI 侧继续只用 ctx.onCleanup。

尚未实现

下面三项在文档里不写成已有能力，属于路线图：

项现状
事件补发（after 游标）SubscribeOptions 只有 types / signal / onActivity，没有游标；durable 事件无法从指定位置续订，ephemeral 事件永远无法补发。
permissions 声明ocplugin.json 没有权限字段，安装时也没有逐项授权提示。安装器只校验清单结构，不做权限告知。

容易误解的契约边界

说法实际
「收件箱就是会话消息队列」 不是。session_inbox 是会话的投递队列（用户消息排队、steer / queue、 附件与合成消息），归会话运行时所有，插件不该碰。ctx.inbox 是给用户看的事项列表， 与某个会话的执行顺序无关。详见 4.18。
「requires.opencode 是完整 semver range」 不是。安装器只解析出最低版本再比较：^2.2.5 等价于 >= 2.2.5， 不限制上界。真正的兼容性契约是 apiVersion，它不变就意味着插件 API 兼容。
「configuration 的 enum 可以枚举数字或布尔」 enum 只能配在 string 上；array 只支持 items.type 为 "string"。default 必须与声明的类型匹配 （含 enum 成员、数组元素必须是字符串），否则 manifest 校验直接拒绝安装， 错误为 This plugin bundle has an invalid configuration: ...。

Q: 清单里声明了 entry.gui，界面为什么不出来？

按顺序检查这四项：

  • entry.gui 是 gui/main 这类以 /main 结尾的路径，不是带扩展名的文件名。
  • 产物是 gui/main.cjs 或 gui/main.js 的 CommonJS 文件，不含 import/export 语句。
  • 在桌面端运行；Web 端不加载第三方界面。
  • 插件处于启用状态。

Q: 能做独立桌面窗口吗？

公开 API 只提供已有窗口的读取（ctx.windows）与页面嵌入（ctx.embeds）。 主进程入口可以 require("electron") 自行创建窗口，但属于非公开路径，升级不保证兼容， 也不受插件生命周期管理。哪些能力只差暴露、哪些要改架构、哪些明确不做，见上文「能力边界」。

Q: 能不能直接改 OpenCode 的内置界面？

不能替换内置组件的渲染逻辑。可以新增注册表条目、插槽内容，或注入 CSS 与主题； 与内置插件同 id 的插件会被判定冲突，界面不加载。

Q: 为什么工具参数校验失败？

input 用了 Effect Schema，字段名与类型必须与模型传入一致。给字段加 Schema.optional 可以让参数变为可选。

Q: 打包后安装提示校验失败？

检查生成校验和的是否就是最终写入压缩包的字节。先写文件再计算哈希，不要在打包后修改 dist/。

Q: 插件可以同时有服务端与界面吗？

可以，同一个包内放 server/main.ts 与 gui/main.tsx， 清单和 package.json 同时声明两个入口即可。界面通过 ctx.client 或 ctx.rpc 调用服务端。
