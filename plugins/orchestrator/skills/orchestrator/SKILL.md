# Orchestrator

`orchestrator.*` 把一批任务变成一台自动推进的状态机：记账、按依赖派发、收回结构化结果、跑机械核对。它**不做判断**——不拆需求、不裁决冲突、不归因、不合入。判断全部由你（PM）来做。

## 批次生命周期

侦查 → 出任务图 → `plan` → `approve` → 收异常 → `resolve` → 审计 → 合入 → 清理。

1. **侦查**：先看要改的目录、现有测试命令、能不能独立验收。不清楚的地方先查，不要带着问号拆任务。
2. **出任务图**：按下面的判据写 `tasks`，一个任务一条可合并的改动。
3. **`orchestrator.plan`**：提交后所有任务都是「待派」。看返回的 `rejected` 与 `conflicts`，`rejected` 必须改完重新提交（换 `planID`），`conflicts` 要你决定怎么串。
4. **`orchestrator.approve`**：省略 `tasks` 就是放行整个就绪层，插件按 `concurrency` 立即派发，返回 `dispatched` 与 `waiting`。
5. **收异常**：过一段时间调 `orchestrator.status`。正常任务只有计数，**异常逐条列出**。没有异常就不要打扰任何执行会话。
6. **`orchestrator.resolve`**：对每条异常按下面的矩阵裁决。
7. **审计**：一个任务进入「已核」后，你读它的结果与 diff，自己决定合不合、怎么合。
8. **合入**：合入之后调 `resolve merged`，把「已核」推到「已合入」。下游任务只有看到依赖全部「已合入」才会被派发。
9. **清理**：全部任务进「已合入」或你明确放弃后，批次结束。插件不自动删 worktree 与分支。

## 拆任务的判据

一个任务必须同时满足：

- **可验收**：能写成命令，失败时退出码非零。写不出验收命令，说明任务粒度不对。
- **路径不重叠**：`allowPaths` 与同时在跑的其他任务没有前缀交集。冲突不会自动串行化，插件只报告。
- **可独立回退**：撤销这一个任务不影响别的任务。跨模块的原子改动应该是一个任务，不是三个。

反例：把「加接口」「改调用方」「补测试」拆成三个任务——它们互相依赖又共享路径，等于给自己制造异常。

## 并行判据

两个任务能同时跑，当且仅当：

1. `allowPaths` 没有前缀交集；
2. 验收命令互不干扰（不要两个任务都跑全仓 `bun test` 又改同一个包）；
3. 正在进行的任务数没到 `concurrency`。

依赖链上的任务不算冲突：它们本来就不会同时就绪。拿不准就降低 `concurrency`，串行比异常便宜。

## 异常处理矩阵

`status` 里的 `kind` 决定下一步：

| kind | 通常原因 | 你的动作 |
| --- | --- | --- |
| `验收失败` | 执行者没跑绿，或跑了但结果不对 | 读 detail 末 30 行，判断是任务没做完还是验收命令本身错了。任务没做完 → `retry`；命令写错 → 改 plan 重新提交。 |
| `执行失败` | 会话执行报错 | 看错误是不是环境问题。可恢复 → `retry`；需求本身站不住 → `abandon`。 |
| `会话失联` | 执行会话消失 | 先确认 worktree 与分支还在。在 → `retry` 会新建分支重做；不在 → `abandon`。 |
| `结果缺失` | 没写结果文件、写了非法 JSON、commit 不是 HEAD、worktree 没了 | 判断是执行者漏了收尾，还是它压根没提交。补得回来 → `retry`；补不回来 → `abandon`。 |
| `范围越界` | 改到 `allowPaths` 之外，或有已跟踪文件未提交 | **不要 accept**。要么你确认那些改动确实属于本任务，用 `accept` 并写清理由；要么 `retry` 并收紧任务书；要么 `abandon`。 |
| `超时` | 跑太久，可能卡住 | 看会话是否还在干活。在 → 等；不在 → `retry`。 |
| `阻塞` | 上游被放弃 | 决定还等不等那个上游：不等 → `unblock` 让它回待派；等 → 先处理上游。 |

五个 `decision`：

- `retry`：失败任务重做，**保留批准**，有空位立即重派，并新建分支（`task/<id>-r<n>`），不在旧分支续写。
- `merged`：`已核 → 已合入`，下游解锁。**只有真正合入之后才调**。
- `unblock`：`阻塞 → 待派`。上游放弃后你决定不再等它。
- `abandon`：任务失败不再重试，依赖它的任务全部标 `阻塞`。必须给 `note` 写清原因。
- `accept`：越过验收失败直接进 `已核`，**必须带 `note`**。只在瑕疵可接受、且你准备在合入时自己处理时用。

状态不匹配的 `resolve` 会直接报错，不会被静默忽略——报错说明你判断错了状态，先 `status` 再看。

## 回传只读指针，机械项自己跑

- 执行者写结果文件，**不给你发进度消息**。你只在三种情况下会收到执行会话的消息：卡住超过 30 分钟、需要需求没写的决策、必须改 `allowPaths` 之外的路径。
- 收到这类消息，给决定，不要让对方写报告。
- 验收命令由插件原样执行，你不需要重跑；但**合入前的审计**（读 diff、看是否符合需求）是你的活，插件不做。
- 结果里的 `commit`、`changed`、`verify` 是给你审计用的指针，不是结论。

## 什么时候不用插件

- 任务数 ≤ 3：直接手动开会话、手动 `deliver`，比建台账快。
- 只有一条串行链：没有并行、没有依赖分叉，插件的价值只剩记账。
- 需要频繁改需求：任务图会一直重提交，不如边做边拆。

插件适合的是：任务多、依赖成图、能并行、每个任务都能独立验收的批次。

## 工具速查

| 需求 | 工具 |
| --- | --- |
| 提交任务图 | `orchestrator.plan` |
| 看进度与异常 | `orchestrator.status` |
| 放行并派发 | `orchestrator.approve` |
| 裁决一条异常 | `orchestrator.resolve` |

`plan` 相同 `planID` 且输入一致是幂等的；输入不同会报错，换一个 `planID`。
